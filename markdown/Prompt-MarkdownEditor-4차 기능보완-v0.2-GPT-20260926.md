## 0. 최상위 실행 지시

너는 AI, Python, Markdown·HTML 문서 포맷, Windows 자동화, PySide6, QtWebEngine, 데스크톱 GUI에 능숙한 시니어 개발자다.

프로젝트 루트에서 이 프롬프트와 PRD, 기존 코드·테스트·문서를 직접 읽고 곧바로 구현하라. 설명, 설계안, 의사 코드, 일부 샘플만 작성하고 멈추지 말라. 실제 프로그램을 수정하고 의미 있는 자동 테스트를 추가하며, 실사용 샘플 검증, 한국어 문서, Windows 배포 산출물까지 현재 코드와 일치하도록 갱신하라.

다음 규칙은 모든 절보다 우선한다.

1. 실제 파일·코드·실행 결과가 이 문서의 추정보다 우선한다.
2. 기존 구현을 폐기하고 처음부터 다시 만들지 말고, 현재 구조와 기능을 조사한 뒤 필요한 부분만 안전하게 리팩터링한다.
3. PRD, 이 프롬프트, 기존 프롬프트, `samples` 원본은 수정·삭제·이동하지 않는다.
4. 사용자가 이미 수정한 파일과 이번 작업과 무관한 변경을 되돌리거나 덮어쓰지 않는다.
5. 실행하지 않은 검사는 절대로 `PASS`라고 기록하지 않는다. GUI 세션이나 권한이 없어 실행하지 못한 검사는 이유와 함께 `NOT_CHECKED`로 기록한다.
6. 샘플의 편집·저장·닫기 검사는 부속 폴더까지 포함한 임시 복사본에서 수행한다. 프로젝트의 원본 샘플은 읽기 전용으로 취급하고 검증 전후 SHA-256을 비교한다.
7. 구현 중 오류가 발생하면 원인을 조사하고 수정한 뒤 관련 검사와 회귀 검사를 다시 실행한다. 한 번 실패했다는 이유로 계획 설명만 남기고 중단하지 않는다.
8. 권한 승인, GUI 세션 부재, 필요한 외부 자산 부재처럼 직접 해결할 수 없는 조건만 차단 사유로 인정한다. 차단되지 않은 항목은 계속 수행한다.
9. 코드 식별자는 영어로 작성하고, 사용자 UI·문서·오류·최종 보고는 자연스러운 한국어로 작성한다.
10. 모르는 사실은 추측하지 말고 모른다고 기록한다.

## 3. 필수 요구사항

### R4-01. 편집기 글자 간격 조절

#### UI

- 상단 메뉴의 `보기(V)` 메뉴에 다음 액션을 추가한다.
  - `글자 간격 크게`
  - `글자 간격 작게`
- PRD의 “글간격”은 일반 사용자가 이해하기 쉬운 UI 문구인 “글자 간격”으로 표시한다. PRD 원문과 다른 이유를 `docs\DECISIONS.md`에 기록한다.
- 이 기능은 왼쪽 Markdown 편집기의 글자 간격만 바꾼다. 오른쪽 Viewer의 CSS 자간은 변경하지 않는다.

#### 동작 기준

- Qt의 `QFont.PercentageSpacing`을 사용한다.
- 기본값은 `100%`, 한 단계는 `5%p`, 최솟값은 `80%`, 최댓값은 `150%`로 확정한다.
- `글자 간격 크게`는 현재 값에 `5`를 더하고, `글자 간격 작게`는 `5`를 뺀다.
- 범위를 넘지 않도록 clamp하고, 경계에서 다시 누르면 값은 유지하면서 상태 표시줄에 한국어 안내를 표시한다.
- 변경 결과는 현재 탭뿐 아니라 열려 있는 모든 편집기와 이후 새로 여는 탭에 동일하게 적용한다.
- `QSettings`의 별도 키에 저장하고 다음 실행에서 복원한다. 잘못된 설정값은 기본값으로 안전하게 복구한다.
- 기존 글자 크기 조절과 독립적이어야 한다. 글자 크기를 바꾼 뒤에도 글자 간격 비율이 유지되고, 반대 순서도 동일해야 한다.
- Pretendard 글꼴, 구문 강조, 줄 번호 폭, 한글 IME, 커서·선택 범위, undo/redo 내용에는 부작용이 없어야 한다.
- 상태 표시줄에 변경된 값을 예: `편집기 글자 간격 105%`처럼 표시한다.

#### 구현 주의사항

- `QFont`를 매번 새 기본 글꼴로 교체해 기존 글꼴 크기·weight·family를 잃지 말라. 현재 편집기 폰트를 복사해 letter spacing만 바꾼다.
- 탭별 문서 내용에 글자 간격을 저장하지 말고 애플리케이션 전역 보기 설정으로 관리한다.
- 플랫폼별 픽셀 값 대신 백분율을 사용해 Windows 배율과 글자 크기에 따라 자연스럽게 확대되도록 한다.

### R4-02. 여러 Markdown 문서를 편집하는 문서 탭

#### 레이아웃

- 중앙 작업 영역 상단에 `QTabWidget` 또는 동등한 Qt 탭 UI를 추가한다.
- 각 탭은 Markdown 문서 한 개와 그 문서의 왼쪽 편집기·오른쪽 Viewer 쌍을 소유한다.
- 메뉴와 Markdown 서식 툴바는 애플리케이션 전역으로 하나만 두고, 항상 활성 탭에 작동시킨다.
- 탭 제목은 기본적으로 파일명만 표시하고, 전체 절대 경로는 tooltip으로 제공한다.
- 수정된 탭 제목과 메인 창 제목에는 `*`를 표시한다.
- 탭은 닫기 버튼을 제공하고, 사용자가 문서 순서를 바꿀 수 있도록 이동 가능하게 한다.
- 탭이 하나뿐이어도 탭 표시줄을 유지해 현재 문서가 어느 탭인지 일관되게 보여 준다.
- 열려 있는 문서가 없을 때는 문서 관련 저장·서식·Sync Scroll 액션을 안전하게 비활성화한다. PRD에 없는 임의의 미저장 새 문서를 자동 생성할 필요는 없다.

#### 문서 세션 구조

- 단일 `MainWindow` 필드에 모든 문서 상태를 저장하는 현재 구조를 그대로 복제하지 말라.
- `DocumentSession`, `DocumentTab`, `DocumentWorkspace` 등 책임이 명확한 단위를 도입한다. 이름은 코드 구조에 맞게 선택할 수 있다.
- 문서 세션은 최소한 다음을 소유하거나 명확하게 참조해야 한다.
  - `LoadedDocument`와 현재 경로
  - `MarkdownEditorWidget`
  - `PreviewPane`
  - 해당 문서의 splitter
  - render debounce 타이머와 revision
  - 링크 검사 결과와 렌더 상태
  - Sync Scroll 타이머·보호 플래그
  - 날짜 저장 세션 정보
- `MainWindow`는 메뉴·툴바·전역 설정·최근 파일·활성 탭 전환·앱 종료를 조정한다.
- 기존 테스트와 호출부를 위해 `window.editor`, `window.preview`, `window.document_data` 같은 속성이 필요하면 활성 세션을 반환하는 읽기 전용 호환 property로 제한한다. 문서 상태의 실제 저장소를 다시 전역 단일 필드로 만들지 않는다.

#### 파일 열기

- `파일 > 열기`는 한 번에 하나 이상의 Markdown 파일을 선택할 수 있게 한다.
- 새 파일을 열면 기존 탭을 교체하지 않고 새 탭에 추가한다.
- 최근 파일, 명령줄 인자, 내부 Markdown 링크, 드래그앤드롭도 동일한 공통 열기 함수로 들어가야 한다.
- 이미 열린 파일을 다시 열면 중복 탭을 만들지 않고 기존 탭을 활성화한다.
- 중복 판정은 실제 존재하는 파일의 정규화된 절대 경로를 기준으로 하며 Windows의 대소문자 비구분을 고려한다. 심볼릭 링크·상대 경로에 대한 실제 동작은 테스트하고 결정 근거를 기록한다.
- 한 파일 열기에 실패해도 이미 열린 탭과 다른 정상 파일은 유지한다. 여러 파일을 열 때 성공·중복·실패 수를 한국어로 요약한다.

#### 탭 전환과 상태 갱신

- 탭 전환 시 메인 창 제목, 상태 표시줄, 연결 문제 패널, 메뉴 체크 상태와 활성화 상태가 활성 문서를 정확히 반영해야 한다.
- 전역 설정인 테마, 글자 크기, 글자 간격, 자동 들여쓰기, 외부 이미지 허용, Sync Scroll 설정은 모든 기존 탭과 새 탭에 적용한다.
- 문서별 커서, 선택, 편집기·Viewer 스크롤, undo/redo, 수정 여부는 탭 전환 후 그대로 유지한다.
- 비동기 렌더 결과는 해당 세션의 revision과 생존 여부를 확인한 뒤 그 세션 Viewer에만 반영한다. 닫힌 탭이나 다른 활성 탭에 늦은 결과를 적용하지 않는다.
- `Sync Scroll 위치맞춤`과 편집기/Viewer 양방향 스크롤은 활성 탭에만 작동한다.

#### 탭 닫기와 앱 종료

- 탭 닫기 버튼과 `Ctrl+W`로 활성 탭을 닫을 수 있게 한다.
- 수정되지 않은 탭은 즉시 닫는다.
- 수정된 탭은 해당 파일명을 포함한 `[저장] [저장 안 함] [취소]` 대화상자를 표시한다.
- `[취소]`를 누르면 탭을 닫지 않는다. `[저장]`이 취소되거나 실패해도 탭을 닫지 않는다.
- 여러 수정 탭이 있는 상태에서 앱을 닫으면 각 수정 문서의 처리를 확인하고, 어느 단계에서든 취소하면 아직 닫히지 않은 모든 탭과 앱을 유지한다.
- 탭을 닫을 때 해당 WebEngine, 타이머, signal 연결, 작업 객체를 정리해 닫힌 문서가 이후 상태를 변경하거나 리소스를 계속 점유하지 않게 한다.
- 마지막 탭을 닫아도 애플리케이션은 종료하지 않고 빈 작업 영역으로 남는다.

#### 저장

- `Ctrl+S`, 날짜 붙여 저장, 다른 이름으로 저장, 파일 위치 열기는 활성 탭에만 적용한다.
- 한 탭을 저장해도 다른 탭의 수정 표시와 원본 메타데이터가 바뀌지 않아야 한다.
- 다른 이름으로 저장한 경로가 이미 다른 탭에서 열려 있으면 덮어써서 두 탭이 같은 파일을 가리키게 하지 말고, 충돌을 알린 뒤 기존 탭을 활성화한다.
- 기존 인코딩·BOM·줄바꿈·끝 줄바꿈 보존과 원본 불변 규칙을 그대로 유지한다.

### R4-03. Explorer 파일 드래그앤드롭 열기

#### 대상 영역

- Windows Explorer의 Markdown 파일을 다음 영역에 놓으면 열려야 한다.
  - 메인 창의 빈 영역
  - 왼쪽 Markdown 편집기와 그 viewport
  - 오른쪽 Viewer의 컨테이너와 실제 `QWebEngineView`
  - 문서 탭 표시줄 또는 탭 페이지
- `QPlainTextEdit`와 `QWebEngineView`가 drop 이벤트를 자체 소비할 수 있으므로 메인 창의 `dropEvent()` 하나만 구현해서 완료로 간주하지 않는다. 자식 위젯 subclass, event filter 또는 공통 drop controller를 사용해 실제 대상 영역에서 검증한다.

#### 입력과 동작

- `QMimeData.urls()`에 포함된 로컬 파일 URL만 처리한다.
- 지원 확장자는 기존 Markdown 확장자 정책과 동일하게 `.md`, `.markdown`, `.mdown`, `.mkd`, `.mkdn`이며 대소문자를 무시한다.
- 여러 Markdown 파일을 한 번에 놓으면 전달 순서대로 각각 새 탭에 열고 마지막으로 성공한 파일을 활성화한다.
- 이미 열린 파일은 중복 탭 대신 기존 탭을 활성화한다.
- 한글, 공백, 괄호, 긴 경로가 있는 로컬 파일을 지원한다.
- 디렉터리, 존재하지 않는 파일, 원격 URL, 지원하지 않는 확장자는 열지 않는다. 유효한 파일과 무효한 항목이 섞여 있으면 유효한 파일은 열고 무효 항목은 한국어 요약 경고로 알린다.
- drop된 파일 경로나 `file:///` 문자열이 편집기 본문에 삽입되어서는 안 된다.
- drop으로 기존 탭을 교체하거나 기존 수정 문서에 저장 확인을 요구하지 않는다. 정상 파일은 새 탭으로 추가한다.
- drag enter/move 단계에서는 처리 가능한 로컬 Markdown 파일이 하나라도 있을 때만 복사 동작을 허용한다.
- Explorer drop, 파일 메뉴, 최근 파일, 명령줄, Markdown 링크가 파일 검증·중복 처리·오류 표시를 공유하도록 공통 열기 경로를 사용한다.

## 4. 권장 UI와 접근성 세부사항

- 탭 닫기 버튼과 수정 표시가 라이트·다크 모드 모두에서 식별되어야 한다.
- 파일명이 길면 탭이 무한히 넓어지지 않도록 elide를 사용하되 tooltip에는 전체 경로를 보존한다.
- 탭 전환과 파일 열기 성공·실패를 색상만으로 알리지 말고 상태 표시줄 텍스트를 함께 사용한다.
- 메뉴 액션에는 기존 mnemonic 규칙을 따르고 단축키 충돌을 자동 검사한다.
- `Ctrl+Tab`/`Ctrl+Shift+Tab`은 Qt의 표준 탭 이동 동작을 유지한다.
- `Ctrl+W`는 탭 닫기에 사용하고 앱 전체 종료 단축키와 충돌하지 않게 한다.
- 화면 배율 100%와 150%에서 탭 제목, 닫기 버튼, 메뉴 문구가 잘리지 않는지 확인한다.

## 6. 자동 테스트

기존 테스트를 삭제하거나 assertion을 약화해 통과시키지 말라. 구조 변경으로 테스트 fixture를 수정할 때도 기존 사용 시나리오의 의미를 유지한다.

### 6.1 단위 테스트

최소한 다음을 순수 로직 또는 작은 Qt 단위로 테스트한다.

1. 글자 간격 기본값, `5%p` 증가·감소, `80~150%` clamp
2. QSettings의 정상값·문자열·범위 밖 값 복원
3. Windows 경로 정규화와 열린 문서 중복 키 생성
4. drop MIME에서 로컬 Markdown 파일만 추출
5. 여러 URL의 입력 순서 보존
6. 원격 URL·디렉터리·없는 파일·지원하지 않는 확장자 분류
7. 기존 파일 I/O·저장·렌더·편집 순수 로직 회귀

### 6.2 GUI·QtWebEngine 통합 테스트

실제 Qt 위젯과 `pytest-qt`를 사용해 최소한 다음을 검증한다.

1. `보기 > 글자 간격 크게/작게`가 실제 편집기 `QFont` 값을 한 단계 변경한다.
2. 글자 간격이 최솟값·최댓값을 넘지 않고 QSettings를 통해 새 창에 복원된다.
3. 두 탭을 열었을 때 각각 올바른 파일 원문과 Viewer DOM을 표시한다.
4. 탭 A 편집이 탭 B의 텍스트·수정 상태·렌더 결과·문서 기준 디렉터리를 바꾸지 않는다.
5. 탭 전환 후 커서, 선택, undo/redo, 편집기 스크롤, Viewer 스크롤이 보존된다.
6. 느린 이전 렌더가 늦게 끝나도 다른 탭 Viewer에 적용되지 않는다.
7. 같은 파일을 메뉴·최근 파일·상대 경로로 다시 열면 기존 탭이 활성화되고 탭 수가 늘지 않는다.
8. 한 탭 저장 후 다른 수정 탭의 `*`가 유지된다.
9. 수정 탭 닫기의 저장·저장 안 함·취소 세 경로를 검증한다.
10. 여러 수정 탭이 있는 앱 종료에서 취소하면 창과 모든 탭이 유지된다.
11. 탭 닫기 후 늦은 타이머·렌더 callback이 오류를 내거나 상태를 변경하지 않는다.
12. 편집기 영역 drop으로 Markdown 파일이 새 탭에 열린다.
13. Viewer의 실제 `QWebEngineView` 영역 drop으로 Markdown 파일이 새 탭에 열린다.
14. 여러 파일 drop은 여러 탭을 만들고, 중복은 하나만 유지한다.
15. 무효 drop은 본문에 URI 텍스트를 삽입하지 않고 기존 탭을 손상시키지 않는다.
16. 라이트·다크 모드, Mermaid 대비, Sync Scroll, 글자 크기, 들여쓰기, 저장, 보안 기존 GUI 테스트가 계속 통과한다.

GUI 이벤트 합성이 운영체제 Explorer와 완전히 같지 않다면 event filter의 실제 이벤트 경로와 공통 처리 함수를 각각 검증하고, 최종 인수 검증에서 실제 Windows GUI drop을 추가로 확인한다. 자동화하지 못한 실제 Explorer 조작은 자동 통과로 기록하지 말라.

### 6.3 테스트 품질

- 테스트마다 격리된 `QSettings`와 임시 디렉터리를 사용한다.
- 테스트 순서에 의존하지 않는다.
- `QTest.qWait()`만 길게 호출해 우연히 통과시키지 말고 signal 또는 조건 기반 대기를 사용한다.
- WebEngine 렌더는 revision과 DOM 상태를 확인한다.
- 테스트가 0개 수집된 경우 성공으로 보고하지 않는다.
- 통과, 실패, skip, deselected 수를 구분해 최종 보고에 기록한다.

- 실제 Explorer drag/drop을 도구 제약으로 수행하지 못했다면 자동 Qt drop 검증과 구분하여 `NOT_CHECKED` 사유를 기록한다.

## 9. Windows 배포 갱신

소스 검증이 끝난 뒤 기존 `scripts\build_windows.py`를 사용해 다음 산출물을 다시 만든다.

- `build\MarkdownEditor-Setup-0.1.0-Windows-x64.exe`
- `build\MarkdownEditor-0.1.0-Windows-x64.zip`
- 압축 해제 배포 폴더
- `build\build_manifest.json`
- `build\SHA256SUMS.txt`
- `build\BUILD_REPORT.md`

PRD가 버전 변경을 요구하지 않으므로 현재 프로젝트 버전을 임의로 올리지 않는다. 단, 실제 저장소에 별도 버전 정책이 있으면 이를 따르고 근거를 기록한다.

배포 검증은 최소한 다음을 포함한다.

1. 설치본 또는 휴대용 배포본에 새 탭 관련 Python 모듈과 자산이 포함되어 있는지 확인
2. 격리된 `build` 하위 테스트 경로에 설치
3. 설치된 실행 파일로 두 샘플을 동시에 열 수 있는 시작 경로 또는 GUI 동작 확인
4. 글자 간격 메뉴와 문서 탭 표시 확인
5. 설치본에서 한글·공백 경로 Markdown 기동 확인
6. ZIP 전체 CRC 검사
7. manifest, `SHA256SUMS.txt`, 실제 파일 SHA-256 일치 확인
8. 검증용 임시 설치·압축 해제 폴더를 정확한 경로 확인 후 제거

설치 EXE와 실행 파일은 코드 서명되지 않았으면 그 사실을 계속 명시한다.

## 10. 실행·검증 명령

프로젝트 내부 uv 캐시와 Python 설치 디렉터리를 사용한다. 현재 환경에서 이미 존재하는 설정을 우선 확인한다.

기본 검증 흐름은 다음과 같다.

```powershell
$env:UV_CACHE_DIR = "$PWD\.uv-cache"
$env:UV_PYTHON_INSTALL_DIR = "$PWD\.uv-python"

uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -m "not gui"
uv run --locked pytest -m gui
uv run --locked python scripts\verify_samples.py
uv build
uv run --locked --no-sync python scripts\build_windows.py
```

QtWebEngine 자동 검증에서 GPU 가상화 문제가 실제로 발생한 경우에만 기존 프로젝트의 검증 방식에 따라 `QTWEBENGINE_CHROMIUM_FLAGS` 또는 `--disable-gpu`를 사용하고, 이것이 테스트 환경 우회임을 보고서에 기록한다.

`verify_samples.py --visual-confirmed`와 같은 시각 확인 옵션이 있다면 캡처를 실제로 열어 확인한 뒤에만 사용한다.

## 11. 완료 조건

다음을 모두 충족해야 4차 기능보완 완료로 보고한다.

1. `보기` 메뉴의 글자 간격 증가·감소가 단계·범위·영속성 기준대로 동작한다.
2. 여러 Markdown 파일이 각자의 편집기와 Viewer를 가진 탭으로 동시에 열린다.
3. 탭별 문서·렌더·스크롤·수정·저장 상태가 섞이지 않는다.
4. 중복 파일 열기는 기존 탭을 활성화한다.
5. 수정 탭 닫기와 여러 수정 탭의 앱 종료에서 저장·버림·취소가 안전하게 동작한다.
6. Explorer Markdown 파일을 편집기와 실제 Viewer 영역에 drop해 열 수 있다.
7. 다중 파일, 한글·공백 경로, 중복, 무효 drop이 정의된 기준대로 처리된다.
8. 기존 단위·GUI 테스트와 새 테스트가 통과한다.
9. 두 실사용 샘플을 동시에 연 다중 탭 인수 검증과 원본 불변 검사가 완료된다.
10. 라이트·다크, Mermaid 대비, Sync Scroll, 저장, 보안 등 기존 핵심 기능에 회귀가 없다.
11. 한국어 README·사용설명서·아키텍처·결정 기록·진행 문서가 실제 구현과 일치한다.
12. Windows 설치 EXE와 휴대용 ZIP을 재빌드하고 설치본 기동·CRC·SHA-256을 검증한다.

## 12. 최종 보고 형식

최종 답변은 한국어로 다음 순서에 맞춰 간결하지만 검증 가능하게 작성한다.

1. 4차 기능 구현 결과 요약
2. 주요 변경 파일의 절대 경로
3. 글자 간격의 실제 단계·범위·저장 키
4. 탭 구조와 전역/문서별 상태 분리 방식
5. 편집기·Viewer drag/drop 처리 방식
6. 테스트 명령별 통과·실패·skip·deselected 수
7. 샘플 인수 검증 상태 집계, 전체 상태, 보고서와 캡처 절대 경로
8. Windows 배포 산출물의 크기와 SHA-256
9. `WARN`, `NOT_CHECKED`, 알려진 제한과 정확한 이유
10. 사용자가 해야 할 후속 조치가 있을 때만 해당 조치

계획을 작성했다는 사실이 아니라 실제 코드, 실행 로그, 테스트, 캡처, 해시를 증거로 완료 여부를 판단하라.
